# TraceKV 联调接口规范 v0.2（实施协议）

状态：2026-11-12 确定的下一轮联调协议。本文规定三人交接的数据、目录和验收口径；**不表示所有字段和入口已经实现**。当前可运行的 HTTP 与快照契约仍是 [`interfaces.md`](interfaces.md) 中的 MVP v0.1，`contracts/schema.py` 只校验该版本的基础字段。实施时先保持快照 `schema_version: "0.1"`，增加扩展字段；等各端和校验器同步完成后再升级版本号。原始调度事件独立使用整数 `schema_version: 1`，两者不能混用。

## 1. 数据流和模块边界

```text
统一实验入口（队长）：配置、run_id、进程生命周期、目录
  ├─ 请求客户端（队长） → requests.jsonl、summary.json
  ├─ eBPF 调度采集（邓智文） → sched_events.jsonl、sched_summary.json
  ├─ GPU/系统采样（邓智文） → gpu_samples.jsonl、system_samples.jsonl
  ├─ vLLM /metrics 适配（队长） → kv_samples.jsonl
  └─ CPU LRU 事件（侯振宇） → kv_transfers.jsonl、kv_cpu_occupancy.jsonl
                     ↓
             对齐、校验、离线报告（队长）
                     ↓
           下一轮配置建议（侯振宇）
```

eBPF 负责操作系统事件；vLLM `/metrics` 和 CPU offloading 事件负责 KV 语义。GPU 遥测来自 `nvidia-smi`，属于整卡采样。任何整机/整卡指标均不能直接归因于某条请求。HTTP 展示是读取同一份实验数据的可选入口；实验的核心入口是命令行。

## 2. 全局约定

| 项目 | 约定 |
| --- | --- |
| `run_id` | 一次实验唯一、非空、适合目录名；入口生成并传给各采集器；不得由各模块自行再生成。每组策略、每次重复各有独立 `run_id`，用 `comparison_id` 关联对照组。 |
| 时间 | 跨模块交换的时间为 ISO 8601 UTC（末尾 `Z`）；内核与迁移事件保留单调时钟纳秒。不同机器的单调时钟绝不能直接相减。 |
| 时间锚点 | `sched_summary.json` 提供同一台机器的 `start_wall_ns`、`start_monotonic_ns`；映射公式 `wall_ns = start_wall_ns + event_monotonic_ns - start_monotonic_ns`。没有有效锚点时禁止把调度事件与 UTC 请求/GPU 样本关联。 |
| 采样窗口 | 左闭右开 `[start, end)`；用 `window_start_utc`、`window_end_utc` 和实际 `window_ms` 表示。最后一个事件须落入相应窗口；空窗口的分位数为 `null`。 |
| 单位 | 时间：事件 `ns`、调度摘要 `us`、请求/迁移 `ms`；显存和内存：十进制 `MB`；吞吐：`B/s`；比例：0–1。 |
| 缺失数据 | 未采到为 `null`，另附 `source`/`status`/`error`；不能以 0 代替。0 只表示确实观测到零。采集失败时保留已有原始文件。 |
| 数据格式 | 一个 JSONL 文件每行一个 UTF-8 JSON 对象，单行完整；汇总文件为一个 UTF-8 JSON 对象。结果目录只写入自身创建的文件。 |

`request_id` 只标识客户端请求；当前 eBPF 事件中的 `request_id: null` 是预期值。离线对齐只证明时间重叠和统计关联，不能据此声称逐请求因果关系。

## 3. 实验配置与产物

统一入口读取的配置示例（**目标接口，尚无统一启动脚本**）：

```json
{
  "schema_version": 1,
  "comparison_id": "shared-prefix-c1",
  "run_id": "shared-prefix-c1-cpu-lru-r1",
  "model_path": "/models/Qwen2.5-0.5B-Instruct",
  "served_name": "tracekv-model",
  "scenario": "shared_prefix_revisit",
  "workload_path": "workloads/shared_prefix.jsonl",
  "concurrency": 1,
  "requests": 30,
  "warmup": 2,
  "max_tokens": 64,
  "cache_state": "warm",
  "policy": "cpu_lru",
  "gpu_kv_blocks": 33,
  "cpu_kv_blocks": 72,
  "trace_enabled": true,
  "sample_interval_ms": 1000,
  "repeat_index": 1
}
```

`policy` 第一轮只接受 `gpu_only`、`cpu_lru`。`cpu_kv_blocks` 在 `gpu_only` 时为 0；CPU LRU 时为正整数。相同 `comparison_id` 的对照必须固定模型、GPU KV 预算、请求集、并发、生成参数和缓存状态。`manifest.json` 保存上述配置及模型修订、vLLM/系统版本、Git commit、工作负载 SHA-256、启动与结束时间、各采集器的状态。不要仅凭模型路径推断模型版本。

目标目录：

```text
results/<run_id>/
  manifest.json
  requests.jsonl
  request_summary.json
  sched_events.jsonl
  sched_summary.json
  gpu_samples.jsonl
  system_samples.jsonl
  kv_samples.jsonl
  kv_transfers.jsonl
  kv_cpu_occupancy.jsonl
  aligned_snapshots.jsonl
  analysis.json
  report.md
  logs/
```

采集器不可用时，允许相应 JSONL 不存在，但 `manifest.json` 必须记录 `unavailable` 及原因；分析器不得静默跳过后宣称数据完整。现有 `tools/run_kv_lru.py` 把两臂结果写在 `gpu-only/` 和 `cpu-lru/` 子目录下，这属于旧格式；统一入口可以通过适配器读取，或者后续改为每臂独立 `run_id`，不能把两臂原始文件直接混写。

## 4. 采集端 → 分析端

### 4.1 请求记录（队长）

沿用 `tools/benchmark.py` 的 `requests.jsonl`：`request_id`、`case_id`、`started_at_utc`、`success`、`ttft_ms`、`e2e_ms`、`prompt_tokens`、`completion_tokens`、`output_text`、`finish_reason`，失败时附 `error`。统一入口补 `run_id`、`finished_at_utc`；旧文件可由父目录/manifest 补 `run_id`。`ttft_ms` 是客户端收到首个非空可见内容的时间，包含客户端与网络开销；`completion_tokens` 必须取服务端 usage，不能把 SSE 分片数当 token 数。时间对齐只使用 UTC 起止时间，不使用各进程本地的 `perf_counter()` 绝对值。

### 4.2 调度事件与摘要（邓智文）

沿用 `collector/cpu_scheduler.py` 的事件：`run_id`、`metric: "wakeup_to_run_latency"`、`clock: "monotonic"`、`timestamp_ns`（切入时间）、`wakeup_timestamp_ns`、`tid`、`comm`、`cpu`、`value`、`unit: "ns"`。`pid` 目前为 `null`；这意味着**当前数据是整机事件**。若实现目标进程过滤，摘要必须增加 `scope: "target_process"`、`target_pids` 或可核验的线程集合；未过滤时为 `scope: "system"`。不得仅凭 `comm` 相似就标注为目标进程。

`sched_summary.json` 沿用 `stats_to_dict()`，包括锚点、`event_count`、`kernel_matched_count`、`dropped_events_count`、`parser_error_count`、`unmatched_switch_count`、`p50_ns`、`p95_ns`、`p99_ns` 和 `error`。其中 `unmatched_switch_count` 是**无配对唤醒记录的切入**，不能命名为抢占次数。`dropped_events_count` 是内核匹配数与用户态接收数的对账差额；如果内核最终计数缺失，丢失率标记为未知。低样本量或有丢失时，报告要注明分位数限制。

### 4.3 GPU 与系统采样（邓智文）

目标 `gpu_samples.jsonl` 每行包含 `run_id`、`timestamp`、`gpu_index` 或 `gpu_uuid`、`memory_used_mb`、`memory_total_mb`、`utilization_pct`、`temperature_c`、`power_w`、`source: "nvidia-smi"`。每个可选字段单独解析；设备不支持的字段为 `null`。`collector/gpu.py` 已返回主要数值，但尚未产出这种统一的持续采样文件。旧 `tools/run_wsl_baselines.py` 的 `time_utc` 加逗号字符串由适配器转换；旧字符串只有四项，功率位于第 4 项，不能按第 5 项读取。

`system_samples.jsonl` 每行至少包含 `run_id`、`timestamp`、`mem_available_mb`、`source: "proc"`。`disk_read_p95_ms`、`disk_read_bytes_per_s` 当前没有真实采集实现，应为 `null`。系统可用内存是整机指标。

### 4.4 KV 指标与迁移（队长 / 侯振宇）

`kv_samples.jsonl` 每行包含 `run_id`、`timestamp`、`window_ms`、`usage_ratio`、`prefix_hit_ratio`、`running_requests`、`source: "vllm"`。`prefix_hit_ratio` 由相邻两次 Prometheus 计数器差分得到；首样本、查询增量为零或计数器重置时为 `null`。一个持续运行的适配器实例负责整个实验的差分状态，不能每次采样重建。

CPU LRU 使用现有 `tools/tracekv_offload.py` 输出：

- `kv_transfers.jsonl`：`job_id`、`direction`（`gpu_to_cpu` / `cpu_to_gpu`）、`gpu_blocks`、`submitted_ns`、`observed_ns`、`elapsed_ms`、`status`。`elapsed_ms` 是提交到**观察完成**，含队列等待与轮询，不表示纯复制耗时。统一入口补 `run_id`；旧数据可由目录归属补齐。
- `kv_cpu_occupancy.jsonl`：`monotonic_ns`、`operation`、`capacity_blocks`、`occupied_blocks`、`evicted_blocks`。占用块含预留写入中的块位；统一入口补 `run_id`。按同机锚点转换后才能与 UTC 请求记录关联。

真实 CPU LRU 接口只承诺原生 LRU、CPU 容量和迁移事件。`policy/demo.py` 的 `os_aware` 目前是下一轮实验**建议标签**，没有对应可执行缓存实现；不得把它写成已经启用的策略。

## 5. 对齐快照与策略接口

沿用 `contracts/schema.py:validate_snapshot()` 的 MVP v0.1 基础对象：

```json
{
  "schema_version": "0.1",
  "run_id": "shared-prefix-c1-cpu-lru-r1",
  "timestamp": "2026-11-12T10:00:01Z",
  "window_ms": 1000,
  "system": {
    "mem_available_mb": 8192.0,
    "disk_read_p95_ms": null,
    "disk_read_bytes_per_s": null
  },
  "gpu": {"memory_used_mb": 4200.0},
  "kv": {
    "usage_ratio": 0.75,
    "prefix_hit_ratio": 0.42,
    "running_requests": 1
  },
  "sources": {"system": "proc", "gpu": "nvidia-smi", "kv": "vllm"},
  "sched": {
    "scope": "system",
    "event_count": 48,
    "p50_us": 12.0,
    "p95_us": 130.0,
    "p99_us": 240.0
  }
}
```

`timestamp` 代表窗口结束时刻；目标落盘格式另加 `window_start_utc` 与 `window_end_utc`，并保证 `window_ms` 与端点差值一致。`sched` 是扩展对象；现有校验器会保留它，但**尚不校验其中字段**。实施时须增加扩展校验，再让报告依赖它。`sched.p95_us` 仅对该窗口事件计算，不得把整次实验的 `sched_summary.json` 分位数复制到每个时间窗口。现有未配对与丢失计数只有整次实验汇总，应留在 `sched_summary.json`，不得分摊或复制到每个窗口。GPU 样本没有目标窗口内数据时，`memory_used_mb` 为 `null`，`sources.gpu` 记为 `unavailable`；其他域同理。

`policy.demo.recommend_policy(snapshot) -> recommendation` 的现行返回字段是 `run_id`、`policy`（`lru` / `os_aware`）、`bottleneck`、`reason`、`reason_codes`、`apply_mode: "next_run"`。本轮保持旧函数兼容，但在离线分析层增加 `evidence`（字段名、窗口、数值、来源）和 `limitations`。任何建议必须能映射到下一轮**可执行配置**；不能执行的 `os_aware` 标为研究建议，不能当作性能对照组。

HTTP 现有接口 `GET /api/v1/snapshot`、`POST /api/v1/policy/evaluate` 保持不变。前者当前调用旧 `collector.demo` 并固定输出 `gpu.memory_used_mb: null`；接入新聚合器后才会返回真实 GPU 与调度扩展字段。计划中的实验报告 HTTP 路由不属于本轮协议，先以命令行和离线文件验收。

## 6. 状态、异常和验收

`manifest.json` 对每个数据源记录 `status`：`ok`、`unavailable`、`failed`，以及 `error`、实际采样数和时间覆盖范围。`unavailable` 表示环境不具备条件，`failed` 表示启动或运行出错。报告同时呈现请求失败数、采集丢失数、缺失数据和策略执行状态。关联器遇到时钟锚点缺失、`run_id` 不一致、非 UTC 时间或不兼容单位时要报告错误或标记该源不可关联，不能悄悄拼接。

| 交接 | 负责人 | 最低验收 |
| --- | --- | --- |
| 配置、manifest、请求和报告 | 队长 | 同一 `run_id` 贯穿所有文件；同负载、同预算形成可复现对照；报告能追溯原始记录。 |
| 调度、GPU、系统 | 邓智文 | 提供原始事件及摘要；明确整机/目标范围；有锚点、丢失对账和不可用原因。 |
| KV 迁移、占用、建议 | 侯振宇 | 迁移方向/块数/状态、容量与淘汰可核查；建议区分可执行和研究项。 |
| 联合验收 | 三人 | 一次真实推理实验生成请求 + 至少一种系统采集 + KV 证据；对照实验固定配置；采集开销单独测量。 |

开始联调时先用一份带 `run_id` 的固定样例验证字段和时间，再跑真实模型。所有协议更改同时更新本文、样例、`contracts/schema.py`、相应适配器与测试，并在 PR 中列出兼容影响。
