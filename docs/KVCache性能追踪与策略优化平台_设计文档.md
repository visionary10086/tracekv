# 基于 eBPF 的 KV Cache 性能追踪与策略优化平台

版本：v0.3  
日期：2026-10-25  
项目周期：两个月  
文档状态：当前设计方案，尚未完成工程验收和性能验证。

## 1. 项目定位与目标

本项目是面向开源 Linux 操作系统的系统性能分析与优化工具，主要服务于大模型推理开发人员和性能工程师，提供“采集运行数据—定位瓶颈—修改缓存策略—对比验证”的完整流程。

项目围绕三个问题展开：

1. **哪里慢：**关联请求、KV Cache 操作以及 CPU、GPU、存储事件，展示瓶颈证据。
2. **怎么改：**提供已有缓存策略、统一策略接口、策略代码生成和有限的策略组合。
3. **是否有效：**在相同工作负载下，对比修改前后的正确性、性能和资源占用。

首版聚焦大模型推理中的 KV Cache，不将训练中的激活、梯度和优化器状态纳入同一缓存管理范围。

## 2. 应用开发的思路过程

### 2.1 用户痛点

- 推理变慢或显存不足时，难以区分缓存管理、CPU 调度、GPU 数据传输和存储 I/O 的影响。
- 系统指标与推理框架指标相互分离，难以定位具体请求、缓存块和迁移操作。
- 修改缓存策略需要理解框架代码，开发和验证成本较高。
- 不同策略的测试条件不一致，难以判断优化是否有效。

### 2.2 方案演进

最初方案覆盖多框架、多硬件、实时分析、自动修改算法和三级缓存管理。考虑两个月周期，当前方案固定运行环境，以一个真实推理场景贯通完整流程。

保留三个扩展能力，但限定首版实现范围：

| 能力 | 首版范围 | 后续扩展 |
| --- | --- | --- |
| 自动修改算法与策略混搭 | 修改固定接口下的策略配置、插件代码或补丁；支持两种基础策略和一种组合方式 | 任意算法代码理解、复杂策略组合与跨框架自动适配 |
| 自研分配器与三级存储 | 用户态 KV 块管理、CPU/SSD 空间管理、GPU—内存—SSD 迁移控制 | 动态块大小、多设备、复杂预取与更完善的资源调度 |
| 实时平台 | 命令行采集、轻量实时网页、离线报告 | 多用户、多节点、长期在线分析平台 |

### 2.3 首版环境约束

- 首版选择 Ubuntu Server 24.04 LTS（x86_64）作为开发和验收环境，不绑定 openEuler。
- 固定一个 vLLM 版本、一种 NVIDIA GPU 环境和一个主要测试模型。
- 固定模型、框架、驱动及相关依赖版本，提供环境复现说明。
- 其他 Linux 发行版、多推理框架、多 GPU 厂商和训练任务列为后续适配方向，不提前宣称兼容。

发行版已确定；具体系统镜像、内核、硬件、模型和依赖版本需在第一周验证并记录。

### 2.4 Linux 平台选型

采用 **Ubuntu Server 24.04 LTS（x86_64）**。这是面向本项目兼容性和维护周期的选择，不宣称其在所有模型场景中使用率排名第一。

选型依据：

- NVIDIA 的 [CUDA Linux 安装指南](https://docs.nvidia.com/cuda/cuda-installation-guide-linux/)列出了 Ubuntu 24.04 LTS 支持；具体 CUDA 版本仍需核对对应发行版、编译器和驱动要求。
- Ubuntu 官方的[发行周期说明](https://ubuntu.com/about/release-cycle)列明 24.04 LTS 标准安全维护至 2029 年，覆盖项目开发和后续维护需要。
- 推理环境按 [vLLM GPU 安装文档](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/)选择相互匹配的框架、PyTorch、CUDA 和驱动版本，不将各组件的最新版直接拼装。

部署设计：在安装 Ubuntu 的物理机或具备所需权限的 GPU 云主机上开发和验收；eBPF 采集器部署在宿主机，推理进程首版使用独立 Python 环境。容器作为后续复现方式，不代替宿主机内核和权限检查。

第一周分工：A 检查实际内核的 BPF/BTF、追踪点和权限；B 验证驱动、推理框架和 KV 接口；C 固化环境清单、安装脚本和基线测试。操作系统选择已完成，完整软件栈尚未验证。

## 4. 各模块设计方案

### 4.1 工作负载接入模块

通过固定版本的框架适配器获取请求、批次和 KV 块生命周期事件，包括分配、引用、释放、迁出和恢复。优先使用框架已有扩展接口；确需修改框架时，提供明确的版本补丁和复现步骤，不承诺完全零修改。

首版交付一个可运行的适配器，明确能够采集的事件及其粒度。无法获取的指标应标记为缺失或估算。

### 4.2 性能采集模块

- **系统侧：**以 eBPF 采集 CPU 调度、线程等待和存储 I/O 等事件，优先选择稳定追踪点，按需启用用户态探针。
- **框架侧：**记录 KV Cache 语义事件，使系统数据能够关联到具体缓存操作。
- **GPU 侧：**通过 CUPTI、Kineto 等已有接口补充设备计算与数据传输事件，首版选择一条可验证的接入路径。
- **采集控制：**支持过滤、采样、事件缓冲和丢失计数，按场景开启详细追踪。

eBPF 是系统侧采集的核心，但不能单独推断全部 KV 访问，也不能把 CPU 上的 CUDA 函数调用时长直接当作 GPU 实际执行时间。低开销是待测目标。

首版以一种 eBPF 运行方案为主，不同时承诺内核态与用户态运行时的完整适配。

### 4.3 事件关联与性能分析模块

统一时间基准，并记录进程、线程、请求、批次、缓存块、操作类型、数据量、源层级和目标层级等字段。不同时间域需要校准。

初期分析规则关注：

- 缓存容量压力与频繁迁移。
- 同一批数据反复迁出和恢复。
- 迁移等待与请求延迟的重叠。
- CPU 调度等待、存储 I/O 等待和 GPU 传输活动。

输出请求时间线、迁移记录和瓶颈证据。时间上的重叠不直接等于因果关系；无法可靠关联的数据保留为未归属事件，证据不足的结论标为推测。

### 4.4 策略开发与管理模块

内置 LRU、LFU，并提供一种明确的组合方式，例如“先按访问频率筛选候选块，再按最近访问时间选择淘汰对象”。

策略接口允许修改以下决策：

- 缓存块评分和淘汰顺序。
- 迁移目标层级及触发阈值。
- 预取条件和容量配额。

用户输入策略名称或修改要求后，系统生成配置、插件代码或补丁，展示差异，并执行以下流程：

```text
输入要求 → 生成修改 → 接口与语法检查 → 正确性测试
         → 隔离环境运行 → 对照实验 → 用户选择应用或回退
```

策略只能通过受约束的接口提出决策，由核心管理器检查引用保护、容量和合法性。保存策略版本、参数、代码变更和测试结果。

自动修改任意算法代码保留为长期目标；首版不承诺任意输入都能生成正确、高效或兼容的代码。

### 4.5 KV 块管理与三级存储模块

自研用户态块管理与迁移控制，使用固定块大小和明确的容量预算，管理 GPU、CPU 内存、SSD 中的数据位置及生命周期。

GPU 块的所有权必须与推理框架统一，自研管理器通过适配接口协调分配和迁移，避免与框架原有块管理器重复管理同一块内存。CPU 内存池、SSD 空间分配和迁移元数据由本项目管理。

首版优先处理暂不活跃会话和可复用前缀的缓存，保护正在使用的缓存块。缓存标识应包含足以区分模型、配置、前缀位置、数据类型及布局的信息，防止错误复用。

迁移基本流程为：

```text
检查引用与容量 → 分配目标空间 → 复制数据 → 确认完成
              → 发布新位置 → 安全释放源空间
```

需要处理迁移失败、空间不足、重复释放和进程退出。复制失败时不能提前丢弃有效源数据。

验收必须包含真实 KV 数据迁出、恢复和继续推理，不能仅以模拟数据搬运代替。三级存储可能增加延迟；容量收益不等于吞吐提升，也不自动意味着单请求可突破模型上下文限制。

### 4.6 对照实验与评估模块

统一记录模型、依赖版本、硬件、工作负载、策略版本、缓存预算和采集配置。对同一工作负载执行基线与候选方案，检查结果正确性并统计性能差异。

将真实推理测试与存储轨迹回放分开：回放可以验证控制逻辑，不能替代端到端推理性能测试。

### 4.7 展示与交互模块

- 命令行：启动和停止采集、指定策略、运行实验、导出报告。
- 轻量网页：展示缓存占用、迁移速率、请求延迟和采集状态。
- 离线报告：展示时间线、瓶颈证据、策略配置及对照结果。

首版不建设多租户、分布式采集和复杂权限管理系统。

## 5. 实现重点与创新点

### 5.1 实现重点

1. 打通真实 KV 数据的迁出、恢复与继续推理。
2. 保证块生命周期、引用保护和异步迁移的正确性。
3. 将系统事件、框架事件和 GPU 事件可靠关联。
4. 约束自动生成策略的作用范围，并提供测试与回退。
5. 单独测量采集开销，避免工具本身干扰性能判断。

### 5.2 拟验证的创新点

- **面向 KV 的联合诊断：**将缓存生命周期、系统事件和 GPU 传输信息关联，形成可检查的瓶颈证据。
- **可验证的策略修改流程：**连接算法名称输入、代码修改、正确性测试、性能比较和版本回退。
- **考虑迁移代价的策略组合：**结合访问历史、块大小、层级容量和迁移耗时制定决策，并通过实验确定适用场景。

使用 eBPF、提供 LRU/LFU 或搭建网页本身不作为核心创新。创新性与实际收益需要通过实现和对照实验验证。

## 6. 功能测试方案

| 测试对象 | 验证内容 | 预期验收依据 |
| --- | --- | --- |
| 数据采集 | 事件完整性、丢失统计、时间对齐 | 可控事件与采集记录对应，丢失可观察 |
| 事件关联 | 请求、KV 块和迁移关联 | 可追溯关联依据，无法归属的数据明确标记 |
| 块管理 | 分配释放、容量限制、引用保护 | 无重复释放、越界和使用中错误回收 |
| 三级迁移 | GPU—内存—SSD 往返 | 数据校验一致，恢复后推理可继续 |
| 策略执行 | LRU、LFU、组合策略 | 在已知访问序列上符合预期决策 |
| 自动修改 | 无效代码、非法决策、版本回退 | 错误修改被拦截，旧版本可恢复 |
| 分析与展示 | 实时指标、导出报告 | 数据来源一致，结论可追溯 |
| 异常处理 | SSD 满、迁移失败、进程中断 | 不静默使用损坏数据，错误可定位 |

无损迁移的数据复制应进行逐字节或校验和验证。推理结果在可控、确定性条件下与基线比较；存在非确定性时，需要预先定义容差和判定方法。

通过受控 CPU 竞争、存储延迟和缓存容量变化构造已知瓶颈，检验诊断是否能够识别对应证据。

## 7. 性能测试方案与当前状态

### 7.1 对照组

| 编号 | 配置 | 测试目的 |
| --- | --- | --- |
| B0 | 原生框架，不开启平台采集 | 原始性能基线 |
| B1 | 原生框架，开启采集 | 隔离工具采集开销 |
| B2 | 自研三级存储 + LRU | 基础存储与策略效果 |
| B3 | 相同存储管理 + LFU | 比较策略差异 |
| B4 | 相同存储管理 + 组合策略 | 验证组合策略的适用性 |

B2—B4 使用相同资源预算；与 B0 的比较需明确容量、缓存保留方式和成功完成请求数的差异。不能把额外资源带来的收益全部归因于算法。

### 7.2 主要指标

- 吞吐量：输出 token/s、成功请求/s，明确统计时间范围。
- 请求性能：首 token 延迟、生成 token 间隔及其分位数。
- 资源占用：GPU 显存、CPU 内存峰值，区分已分配与预留空间。
- 存储行为：迁移字节数、迁移时长、重复迁移次数、各层占用。
- 工具开销：采集器 CPU/内存使用、事件丢失率、吞吐下降及延迟增加。
- 正确性：迁移数据一致性、推理结果检查、策略测试通过情况。

采集吞吐开销可按 `(未采集吞吐量－采集吞吐量) / 未采集吞吐量 × 100%` 计算，并同时报告绝对值和实验波动。

### 7.3 测试方法

固定模型、输入输出长度、并发度和硬件预算；分别测试冷缓存与热缓存。每组重复运行，建议至少三次，记录波动。高分位延迟需要足够样本，样本不足时注明限制。

同时测试短请求、长上下文、多轮会话及缓存压力场景。容量收益、延迟收益和吞吐收益分别报告，不预设某一策略在所有场景下最优。

## 9. 两个月实施计划

| 时间 | 主要任务 | 阶段验收 |
| --- | --- | --- |
| 第 1 周 | 固定环境，验证框架接入与 KV 数据控制 | 真实 KV 可迁出、恢复并继续推理 |

## 10. 主要风险与应对

| 风险 | 应对方式 |
| --- | --- |
| 框架接口变化、KV 管理侵入性较强 | 固定版本，先做真实数据验证，记录必要补丁 |
| GPU 与系统事件无法准确关联 | 使用可获得的关联标识与时间校准，明确未归属和推测项 |
| SSD 迁移开销超过缓存收益 | 优先不活跃缓存，限制迁移预算，分别报告容量和延迟效果 |
| 自动生成代码不正确 | 限定接口、运行前检查、隔离测试、保存可回退版本 |
| 采集影响工作负载 | 支持过滤与采样，单独设置开销对照组 |
| 两个月范围过大 | 固定单环境、单框架，优先保证真实推理与测试闭环 |

## 11. 提交与交付内容

1. **完整工程：**带注释的源代码、依赖声明、构建脚本和环境建立说明。
2. **设计文档：**开发思路、模块设计、接口约定、实现重点、创新点和已知限制。
3. **测试资料：**功能测试、基准脚本、实验配置、原始结果及与类似项目的比较。
4. **过程性资料：**阶段记录、设计决策、开发历史和线上仓库提交记录。
5. **演示视频：**展示采集、诊断、策略修改、三级迁移及对照结果，在 README 中提供链接。
6. **公开仓库：**按赛事要求公开代码和文档，说明第三方组件、许可证及复现步骤。

演示主线为：运行固定工作负载，采集瓶颈证据，选择或修改缓存策略，完成校验与实验，展示修改前后的正确性和性能结果。

## 12. 三人团队详细分工

### 12.1 分工原则与人员配置

三人按技术链路分工，每人负责实现、模块测试及对应文档。A 负责“看见并解释”，B 负责“正确执行”，C 负责“提出修改并验证效果”。以 A/B/C 代称成员，按实际技术背景匹配，不预设姓名。

本计划按三人能够持续投入八周安排；若主要为课余投入，需要重新核算工期。周数从团队正式启动计算，不代表此前已完成相应工作。第 9 节为总体里程碑，本节细化并行任务。

| 成员 | 主要职责 | 适合的技术背景 | 明确交付 |
| --- | --- | --- | --- |
| A：采集与诊断负责人 | eBPF、GPU 事件接入、统一事件格式、关联分析、采集命令行 | Linux、C/C++、eBPF、性能分析 | 采集器、统一轨迹、诊断规则、开销报告 |
| B：推理与存储负责人 | vLLM 适配、KV 生命周期、用户态块管理、三级迁移、安全执行策略 | PyTorch/vLLM、内存管理、异步编程、CUDA 基础 | 框架适配器、块管理器、迁移引擎、正确性测试 |
| C：策略与实验负责人 | LRU/LFU/组合策略、策略生成、版本管理、对照实验、轻量界面 | Python、测试自动化、基础前后端、算法实现 | 策略插件、生成与校验流程、实验工具、页面和报告 |

B 承担关键路径，A 在前两周协助框架事件设计和 GPU 复制观测；C 从第一周负责基线、测试夹具和结果校验，避免 B 同时承担全部基础设施工作。界面复用现有图表组件，只建设概览、实验对比和策略修改三个必要视图。

### 12.2 A：采集与性能诊断任务

1. 与 B 确定 KV 事件插入位置，与 C 确定实验和配置标识。
2. 实现按目标进程过滤的 CPU 调度、线程等待和存储 I/O 采集；先完成必要事件，再增加细节。
3. 选择一种 GPU 事件接入路径，记录可获得的计算、复制和关联信息。
4. 统一事件结构、时钟映射、事件来源和丢失计数，区分精确关联、估算和未归属数据。
5. 实现基础诊断：缓存压力、重复迁移、迁移等待、CPU 等待和存储等待；每项结论附原始证据。
6. 提供采集启停命令和分析接口，向 C 输出汇总指标与时间线数据。
7. 测量开启与关闭采集的性能差异，完成采集方法和已知限制文档。

验收：一条真实请求能够关联到可获得的缓存与系统事件；未覆盖事件不被假装补齐；采集开销和丢失情况可测量。

### 12.3 B：推理适配与三级存储任务

1. 固定框架版本，梳理 KV 块的分配、引用、释放和可复用条件。
2. 先打通真实 KV 迁出、恢复和继续推理，记录所需框架修改。
3. 实现块元数据、容量预算、引用计数或等价保护、块版本及合法状态转换。
4. 实现 CPU 块池和 SSD 空间管理，通过框架适配接口协调 GPU 块的所有权。
5. 实现迁移队列、完成确认、位置发布和源数据释放；处理失败与空间不足。
6. 向 C 提供只读候选块快照和受约束的策略执行接口，核心管理器拒绝非法决策。
7. 向 A 提供 KV 生命周期事件，完成分配器、迁移和恢复的设计文档。

验收：真实数据往返一致，恢复后可继续推理；正在使用的块不被错误淘汰；失败时不静默丢失有效数据。测试由 B 编写模块检查，C 负责独立的端到端对照验证。

### 12.4 C：策略、自动修改与实验展示任务

1. 从第一周提供固定工作负载、基线运行脚本、实验配置和结果目录规范。
2. 基于冻结的策略接口实现 LRU、LFU 和一种明确组合，编写已知访问序列测试。
3. 将策略名称或自然语言要求转换为配置或插件补丁，展示差异，保存版本。
4. 实现生成代码的语法、接口、行为校验，以及独立进程或受限容器中的实验运行；具体隔离方式需在实现时明确。
5. 实现 B0—B4 对照实验，记录依赖、模型、工作负载、策略版本、失败情况和原始指标。
6. 接入 A 的分析结果，制作轻量实时概览、离线报告和策略对比页面。
7. 整理实验复现说明、README 和演示脚本，汇总三人的文档，不代写其他模块的技术结论。

验收：能够完成“选策略或输入修改要求—查看补丁—通过检查—运行实验—比较结果—选择应用或回退”的流程；失败的策略保留失败记录，不被统计为有效优化。

### 12.7 接口与代码责任边界

以下是拟定接口，不是现有框架 API，具体签名在第一周冻结。

| 接口 | 提供者 → 使用者 | 最少约定 |
| --- | --- | --- |
| 统一事件记录 | B 的 KV 事件、A 的系统/GPU 事件 → A | schema_version、run_id、来源、时间/时钟域、事件类型、可用的请求/块/操作标识 |
| 缓存候选快照 | B → C | 块版本、大小、层级、最近访问、频次、可迁移标记；缺失字段显式标记 |
| 策略建议 | C → B | 候选块及版本、动作、目标层级、原因；B 在执行时重新检查有效性 |
| 执行反馈 | B → A、C | 决策是否接受、实际开始/结束、字节数、错误码与操作标识 |
| 诊断与汇总 | A → C | 指标定义、单位、统计窗口、证据引用、归属或推测说明 |
| 实验配置与结果 | C → A、B | 环境和策略版本、资源预算、负载、采集开关、原始指标位置 |

约定每次实验使用唯一 run_id；缓存块标识需带版本，避免空间复用造成错误关联；字段未知时使用明确的空值，不填伪造值。接口修改需通知上下游并同步更新样例。

建议仓库责任范围：

```text
collector/       A：eBPF 与 GPU 采集

policies/        C：策略与组合
generation/      C：代码生成、校验及版本管理

tests/          各人维护本模块测试，C 组织端到端测试
docs/           各人负责本模块，C 汇总提交材料
```

### 12.8 联调、评审与资源安排

- 每天简短同步已完成、阻碍和接口变更；每周至少一次真实环境联调与演示。
- 第 1 周完成接口样例；测试替身仅用于并行开发，不能替代真实系统验收。
- A 与 B 交叉检查事件语义和迁移时序；B 检查 C 的策略合法性；C 检查 A 的指标是否可复现。
- 若只有一台 GPU 机器，B 优先获得早期迁移开发时段；A 使用独立采集时段；C 在离线测试后预约真实实验。正式基准运行期间禁止其他 GPU 工作负载干扰。
- 性能报告以保存的原始数据为依据；未经重复测试的单次结果标为初步观察。
- 每人持续提交代码和过程记录，并维护本模块复现步骤，避免最后一周集中补文档。

### 12.9 最小可交付范围与进度控制

三人首版必须围绕同一条可验证流程交付：真实 KV 三级迁移、必要的系统/框架/GPU 观测、两种基础策略和一种组合、限定接口内的代码修改与回退、对照实验、轻量实时页面及离线报告。

暂不扩展多模型全面覆盖、多框架、多 GPU 厂商、分布式平台和任意算法自动修改。如果仍无法按期完成，应明确记录延期功能，并与项目负责人重新确定验收范围；不能把未实现功能写成已完成成果。
