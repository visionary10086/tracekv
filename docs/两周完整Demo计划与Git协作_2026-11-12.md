## 1. 交付定义

两周内交付 **TraceKV Demo v0.2**：在一台 Ubuntu WSL + NVIDIA GPU 机器上，用同一个 `run_id` 启动 vLLM 实验，采集真实请求、KV 缓存、GPU 和 eBPF CPU 调度数据；由统一快照给出可解释的下一轮策略建议；运行 GPU-only 与 CPU LRU 对照；生成带原始数据链接的离线报告，并录制一次完整演示。

演示入口以命令行为主，复用已有 FastAPI 快照与推荐接口。模型基线使用已验证的 Qwen2.5-0.5B-Instruct。队长同时尝试 Qwen2.5-3B-Instruct-GPTQ-Int4；若本机量化内核、显存或启动失败，保存错误证据，完整闭环仍以 0.5B 验收。3B 结果须单独列示，不与 0.5B 的吞吐作策略收益比较。

此版本的 `os_aware` 是**根据观测建议下一轮选择 GPU-only 或 CPU LRU 的规则**，不声称已有自研淘汰算法。真实迁移使用 vLLM 0.11.2 已验证的 CPU LRU 路径。SSD 层、任意算法代码生成和复杂策略混搭留给后续版本。

### 最终演示必须出现的六步

1. 运行一个固定配置的测试命令，打印 `run_id` 与结果目录。
2. 发起真实模型请求；至少包含共享前缀、不同前缀和重访场景。
3. 同一实验目录保存请求、vLLM KV 指标、CPU LRU 迁移、GPU 遥测及 eBPF 调度记录；缺失指标标为 `null` 并说明来源。
4. 基于统一快照给出瓶颈、触发规则、策略建议和 `apply_mode=next_run`。
5. 对相同模型、请求序列和 GPU 块预算分别运行 GPU-only 与 CPU LRU，保留输出一致性、命中和迁移证据。
6. 生成 `report.md`、`summary.json`、原始 JSONL 和 3–5 分钟演示视频链接。报告可以显示无收益或负收益，不预设提升比例。

## 3. 必须执行的实验

| 测试 | 固定条件 | 记录与通过条件 |
| --- | --- | --- |
| 接口与逻辑 | 同一模拟快照、非法字段、缺失指标、计数器重置 | 单元测试通过；模拟来源显式标注；不把缺失值写成 0 |
| eBPF 正确性 | 空闲与可控 CPU 争用、同一目标 PID/时间窗 | 有真实事件、时间戳、事件数和丢失统计；目标机器可复现 |
| CPU KV 往返 | 相同短负载，GPU KV 块与 CPU 容量固定 | 输出一致、外部命中与双向迁移可见、无未报告的失败；异常仍保留 |
| 端到端 | 固定模型修订、seed、请求集、并发、上下文与最大输出长度 | 请求、KV、GPU、eBPF 可按 `run_id` 和时间关联；生成完整报告 |
| 采集开销 | 同一负载比较采集关/开，至少 3 轮 | 报告吞吐、客户端 TTFT P50/P95、端到端 P50/P95、失败率、采集器 CPU/RSS；不以单轮差异下结论 |
| 缓存对照 | GPU-only 与 CPU LRU 各至少 3 轮，先固定一个主模型 | 报告前缀命中、迁移块数与提交至完成间隔、显存/CPU 占用、请求延迟及吞吐；明确 CPU LRU 使用额外 CPU 容量 |
| 3B 适配 | GPTQ-Int4 单并发、2048 token 上下文起步 | 模型修订与 SHA 固定，成功请求或完整失败日志；通过后再增加上下文，不将其数据混入 0.5B 对照 |

每轮生成独立目录，不能覆盖旧结果。`nvidia-smi` 是整卡采样，不能当作模型独占 GPU 显存；eBPF 不直接给出 GPU 内核时间或 KV 命中率。只把实际测试通过的能力写进最终演示说明。

## 4. Git 与 GitHub：三人统一工作流

Git 的 **commit** 是把一组修改记录到本地历史，**push** 才把这些提交上传到 GitHub。**分支**让三人同时改代码；**Pull Request（PR）**让其他成员审阅“功能分支 → `main`”的差异；**merge** 把经检查的 PR 合入 `main`。已有功能分支在合并后仍可能留在 GitHub，分支存在不代表未合并。

第一次使用：

```bash
git clone https://github.com/visionary10086/tracekv.git
cd tracekv
git status
```

每次开始新任务，先从最新 `main` 建自己的分支。以下以邓智文新任务为例，其他人分别用 `feat/policy-*`、`feat/integration-*`：

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/collector-integration
```

改完后明确检查并提交文件。`git add` 选具体路径，避免把模型权重、缓存或个人配置带进仓库：

```bash
git status
git diff
git add collector/ tests/ docs/collector-scheduler.md
git diff --cached
git commit -m "feat(collector): integrate scheduler samples with run id"
git push -u origin feat/collector-integration
```

上传分支后创建 PR，填写功能、验证命令、真实结果和局限。可以在 GitHub 页面操作，也可用 CLI：

```bash
gh pr create --base main --head feat/collector-integration --fill
gh pr view --web
gh pr checks
```

由另一位成员审阅代码与证据；队长确认集成测试后在 GitHub 页面合并，或运行 `gh pr merge <PR编号> --squash --delete-branch`。若仓库尚未配置自动检查，`gh pr checks` 显示没有检查不等于测试通过，PR 中仍需写明本地/WSL 测试结果。合并后每个人重新更新本地 `main`：

```bash
git switch main
git pull --ff-only origin main
```

**merge 冲突**通常发生在自己的功能分支落后于 `main`。在功能分支中同步后，按 `git status` 列出的冲突文件处理 `<<<<<<<`、`=======`、`>>>>>>>` 标记，重新运行相关测试，再提交解决结果：

```bash
git switch feat/collector-integration
git fetch origin
git merge origin/main
# 手工处理冲突并运行测试
git add <已解决的文件>
git commit
git push
```

如果暂时无法解决，`git merge --abort` 可回到此次合并前的状态。已推送且被队友使用的分支优先用上述合并方式同步，避免重写他人的提交历史。不要直接向 `main` 推送实验性代码，也不要把模型权重、密钥或完整本地环境上传。
