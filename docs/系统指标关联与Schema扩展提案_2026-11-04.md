## 一、CPU Scheduler 实测数据与指标可信度审查

在 `smoke-003`、`idle`、`load_16`、`load_32` 四组真实 WSL2 内核测试中，累计采集了超过 28,000 条调度事件，核心统计数据对账如下：

| 数据集 | 事件总数 | 内核 Matched | 丢包数 (Drop) | 解析错误 (Error) | 未配对切入 (Unmatched) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| `smoke-003` (2s) | 1,320 | 1,319 | **0** | **0** | 105 |
| `idle` (5s) | 7,967 | 7,966 | **0** | **0** | 157 |
| `load_16` (5s) | 7,542 | 7,537 | **0** | **0** | 229 |
| `load_32` (5s) | 11,978 | 11,963 | **0** | **0** | **8,239** |

### 审查结论
1. **配对与闭环一致性（Reconciliation Consistency）**：
   - 用户态接收事件数与内核配对计数差异在万分之五以内（如 11,978 vs 11,963），完全属于 SIGINT 优雅退出瞬间探针卸载与缓冲队列刷新的正常边界效应。
   - `dropped_events_count` 始终为 **0**，证实 `BPFTRACE_PERF_RB_PAGES=256` 结合 Python 实时管道流式消费在 2,400 events/s 的高吞吐下无任何背压丢包。
2. **指标边界严格性（Metric Definition & Boundary）**：
   - **测量边界**：当前探针严格测量的是 **Wakeup-to-Run（唤醒到就绪切入）延迟**。
   - **抢占风暴可观测性**：计算密集型任务时间片耗尽发生内核抢占时，不经过 `sched_wakeup`，会被精准计入 `unmatched_switch`。在 32 核满载（`load_32`）下，抢占次数从 157 次暴增至 8,239 次（增长 > 35 倍），与 CFS/EEVDF 调度器的抢占行为严格吻合。
3. **时钟对齐可靠性**：
   - 内核纳秒级单调时钟 `bpf_ktime_get_ns()` 与 Python `time.monotonic_ns()` 为同一硬件时钟源（不受 NTP 跳变影响）；通过启动与结束时的 `TimeAnchor(wall_ns, monotonic_ns)`，可精确将单调时钟映射为标准 ISO 8601 UTC。

1. **vLLM 指标（`engine/vllm_adapter.py`）**：
   - 解析 Prometheus `/metrics`，提取 `kv_cache_usage_perc`、`num_requests_running`，并计算相邻采样窗口的 `prefix_hit_ratio` 增量差分。

## 三、时间对齐与关联架构设计

为了实现高频微观内核事件与低频应用语义指标的时间对齐，本次交付了两个核心模块：

### 1. 实时多源聚合器：`collector/aggregator.py`
- 提供统一构建方法 `build_unified_snapshot(...)`。
- 将 `/proc/meminfo`、`collector.gpu`、`engine.vllm_adapter` 和 `collector.cpu_scheduler` 融合。
- **完全兼容性保证**：由于 `contracts/schema.py` 中的 `validate_snapshot()` 明确保留未知扩展字段，聚合器生成的快照既 100% 满足当前 MVP v0.1 字段校验，又携带了高精度的 CPU 调度与 GPU 遥测扩展。

### 2. 离线/批处理时序关联引擎：`collector/correlator.py`
- 将同一实验目录下的三类异步日志进行时序对齐：
  - `sched_events.jsonl`（内核单调时钟纳秒事件）
  - `gpu_samples.jsonl`（UTC 墙钟显存采样）
  - `requests.jsonl`（客户端请求首字延迟 TTFT 与完成令牌数）
- 依据时间校准锚点（`TimeAnchor`），以固定时间步长（如 1.0s 或 0.5s）对齐到相同的时间桶（Time Bucket）中，并自动计算 **Pearson 相关系数 $r$**，定量验证 CPU 调度延迟激增与 TTFT 突变的相关性。

## 四、统一 `run_id`、时间戳与实验数据组织规范

为了避免多模块日志混乱，规范标准如下：

### 1. `run_id` 命名规范
统一遵循 `<experiment_type>-<config>-<timestamp_or_tag>`：
- 单独基准：`baseline-c1-r1`、`sched-idle-001`
- 联合评测：`tracekv-e2e-<model>-<concurrency>-<policy>-<tag>`

### 2. 时间戳基准规范
- **对外暴露与持久化**：统一使用 ISO 8601 UTC 字符串，包含微秒，以 `Z` 结尾（例如 `2026-11-04T17:16:33.123456Z`）。
- **内核事件内部计算**：始终使用 `bpf_ktime_get_ns()` 单调时钟进行 `latency = switch_ns - wakeup_ns` 的差值运算，杜绝时钟漂移或 NTP 回拨影响。
- **采样窗口**：`window_ms` 统一以整数毫秒计，默认 1000ms。

### 3. 标准化实验归档目录结构
所有联合实验统一落盘于 `results/<run_id>/`：
```text
results/<run_id>/
├── manifest.json              # 实验元数据（模型、策略、并发度、Git Commit、系统环境）
├── sched_events.jsonl          # eBPF 原始调度延迟事件流
├── sched_summary.json          # 调度指标分位数与开销摘要
├── gpu_samples.jsonl           # GPU 显存与核心利用率时序
├── requests.jsonl              # 客户端请求记录（TTFT、E2E、Token 数）
├── aligned_snapshots.jsonl     # 时间窗口对齐后的统一快照流
└── summary.json                # 端到端联合分析评估报告
```

## 五、磁盘 I/O 追踪现状梳理与价值评估

### 1. 现有基础与现状缺口
- **共享契约预留**：`contracts/schema.py` 与 `policy/demo.py` 中已预留了 `system.disk_read_p95_ms` 和 `system.disk_read_bytes_per_s`。
- **内核能力确认**：经检查，当前 WSL2 内核 BTF 中完整包含 `tracepoint:block:block_rq_issue` 和 `tracepoint:block:block_rq_complete`。
- **当前缺口**：
  1. 尚无针对 Block 层的 bpftrace 脚本；
  2. 需要区分虚拟磁盘（VHDX 上的 ext4）与 Windows 跨宿主文件系统（`/mnt/c` 走 9p/drvfs）；
  3. 尚无从扇区大小计算吞吐（`bytes/s`）与请求完成延迟（`p95_ms`）的管道。

### 2. 与 KV Cache 性能分析的价值评估
1. **显存/内存逐出至存储分层（KV Cache Offloading）**：
   - 当大模型上下文极长（如 32k/128k tokens）导致 GPU 显存及 Host RAM 均耗尽时，系统需将冷前缀 KV Cache 块置换到 NVMe SSD。
   - 此时磁盘读取延迟（`disk_read_p95_ms`）将直接决定 KV Cache 重载耗时，进而直接阻碍 Prefill 阶段的首字生成。
2. **权重加载与系统级 I/O 抖动干扰**：
   - 动态加载 LoRA 适配器或同一机器运行并发写盘时，引发 Page Cache 挤压。
3. **优先级与边际效应判断**：
   - 在**纯内存推理（In-Memory KV Cache）**基准下，KV Blocks 全程位于 GPU VRAM 与 Host RAM 中，磁盘几乎无 I/O 活动。
   - 因此，**CPU 调度队列争用（CFS/EEVDF 调度延迟）对在线服务 TTFT 的劣化影响远比磁盘 I/O 更加显著、直接且高频**。
   - **实施建议**：下阶段优先完成端到端 CPU 调度延迟与 vLLM TTFT 的联合评测；磁盘 I/O 追踪作为分层存储（Offloading Tier）引入时的补充能力开发。
