# 项目初步计划与三人分工

项目：基于 eBPF 的 KV Cache 性能追踪与策略优化平台  
计划周期：约两个月，从正式启动计算  
目标环境：Ubuntu Server 24.04 LTS + NVIDIA GPU + 固定版本 vLLM  
当前状态：开发与测试计划，尚未提供实际验收结果。

## 一、项目目标

采集大模型推理中的系统性能与缓存数据，定位瓶颈，调整缓存策略，并通过相同工作负载的对照实验验证效果。先完成最小原型，再逐步接入三级存储、策略代码修改与轻量实时展示。

## 二、人员分工与第一周目标

| 成员 | 主要职责 | 第一周明确目标 | 交付与验收 |
| --- | --- | --- | --- |
| 队长（你） | 服务器环境、vLLM 接入、KV 迁移通路、基准测试与整体集成 | 确认硬件和权限，跑通真实模型生成请求，保存一批固定请求的基线结果 | 启动与测试脚本、环境版本清单、原始结果和复现说明 |
| 邓智文 | eBPF 系统追踪、GPU 指标接入、事件关联与瓶颈分析 | 检查内核及权限，先跑通目标进程的 CPU 调度等待或磁盘 I/O 延迟采集，二选一 | 采集脚本、带时间戳和进程标识的原始数据、可控负载验证及 README；其他成员可复现 |
| 侯振宇 | KV Cache、缓存策略、策略组合与修改、策略测试 | 理解缓存块和前缀复用；用 Python 实现固定容量 LRU 模拟器，预留统一策略接口 | 使用重复访问、顺序扫描和热点变化序列测试；淘汰顺序正确、容量不超限，提供代码、测试及结果 |

邓智文通过框架接口获取 KV 语义，不以 eBPF 直接读取 GPU 中的 KV 数据。侯振宇的模拟器用于验证策略逻辑，模拟命中率不能当作真实推理性能收益。

| --- | --- | --- |

第一周不安排复杂页面和自动代码生成。第二周根据真实接入难度复核工期，不以模拟迁移代替真实功能验收。

## 四、必须开展的测试

- **环境与推理：**GPU、依赖和 eBPF 权限可用；真实请求能够生成结果，错误与超时有记录。
- **采集正确性：**使用可控 CPU 或 I/O 活动验证事件、进程过滤、时间戳及丢失统计。
- **策略正确性：**固定序列的命中、淘汰和容量限制符合预期；非法决策被拒绝。
- **迁移正确性：**真实 KV 数据往返校验一致，恢复后可继续推理，使用中的缓存块受到保护。
- **性能对照：**分别比较关闭/开启采集，以及相同资源预算下的基础/候选策略。
- **异常与稳定性：**容量不足、迁移失败、请求取消、版本回退和持续运行。

性能指标包括首 token 延迟、请求总延迟 P95、吞吐量、失败率、显存与内存占用、缓存命中率、迁移量及采集开销。使用相同请求集和配置，区分冷/热缓存，每组至少重复三次，保留原始结果，不预先承诺提升比例。

## 五、协作要求

每周至少一次联调，每人演示实际运行结果。统一实验编号、数据格式和结果目录；代码、测试与过程记录持续提交。队长组织集成，邓智文维护采集指标定义，侯振宇维护策略测试与比较结果，各自负责本模块文档。
